# Changes to the draft WIT, and what building it taught

Research note 10 ("The WASM plugin runtime", section 2, "Draft world") gave a
sketch of the `syrinx:plugin@0.1.0` world and said plainly that it "has not been
checked with `wasm-tools` or a WIT parser". This template is the first code to
parse it, generate both sides from it and run a real component through it. The
owner approved the note's 15 decisions on 2026-10-21, and Syrinx-app #28 builds
the real host from the same WIT, so every change and finding below should go
back to #28 before its WIT is frozen.

How it was checked, on 2026-10-21 (Linux x86_64; Windows is not yet checked):

- `wasm-tools 1.262.0 component wit wit/` parses the package, with and without
  `--features home-widgets`.
- The guest side is generated by `wit-bindgen 0.63.0` for `wasm32-wasip2` (Rust
  1.97.0), and the host side by `wasmtime::component::bindgen!` in wasmtime
  48.0.7. The template's contract tests instantiate the built component and call
  every export.

## Changes made to the draft

Each change is the smallest one that makes the draft parse or load.

### 1. `events.deliver`: the parameter `result` is renamed `outcome`

The draft said `deliver: func(request: request-id, result: outcome);`. `result`
is a WIT keyword, so the parser stops: "expected an identifier or string, found
keyword `result`". WIT allows `%result` as an escaped name, but `outcome` reads
better and needs no escape, so the parameter is now
`deliver: func(request: request-id, outcome: outcome);`. The generated Rust
parameter is named `outcome` on both sides. This changes no type.

### 2. Every item inside `interface widgets` is gated, not only the interface

The draft gated the interface (`@unstable(feature = home-widgets) interface
widgets`) and expected that to cover its contents. wit-parser 0.262 does not
carry the gate inward: with the feature off it reports "found a reference to a
interface which is excluded due to its feature not being activated; this type is
not gated by a feature but its interface is" for the `use` line, and then the
same for each record that uses `icon`. So the `use`, `stat`, `list-item`,
`widget-body` and `snapshot` each carry `@unstable(feature = home-widgets)` as
well. This is what `WIT.md`'s rule "any item that refers to another gated item
must also be compatibly gated" means in practice.

### 3. The world no longer exports `widgets`, even gated

The draft's world ended with `@unstable(feature = home-widgets) export
widgets;`. It parses, and wit-bindgen leaves it out of a guest built without the
feature, but **wasmtime 48's `bindgen!` cannot leave it out of the host**. The
macro sets `resolve.all_features = true` unconditionally
(`wasmtime-internal-component-macro-48.0.7/src/bindgen.rs`, `parse_source`) and
offers no `features` option, so the generated `Plugin::instantiate` requires
every gated export. A plugin built without `home-widgets` then fails to load
with "no exported instance named `syrinx:plugin/widgets@0.1.0`". The template
hit exactly this.

The interface is kept, gated, so #31 can design it; only the export line is
removed from the 0.1.0 world. When #31's plan is approved, widgets should arrive
as an `@since` addition on a later minor (or a separate world that includes
`plugin`), not as an `@unstable` export.

## Findings that answer the note's ⚠️ items

- **Host-side unstable features** (note section 2, scheme item 5): wasmtime 48's
  `bindgen!` compiles every gated item. Gated *imports* (like
  `host.widget-changed`) still work: the generated `add_to_linker` takes a
  `LinkOptions` with one switch per feature (`home_widgets`), so the host links
  them only when switched on, and the template switches none on. Gated
  *exports* do not work (finding 3 above). Hosts must therefore implement every
  gated host function in Rust even while it is off.
- **Interface names carry the version.** `wasm-tools component wit` on the built
  `plugin.wasm` lists `import syrinx:plugin/types@0.1.0`, `import
  syrinx:plugin/host@0.1.0` and `export syrinx:plugin/lifecycle@0.1.0` and so on;
  the test host reads the same names through `Component::component_type()` and
  refuses a component whose exports do not match the manifest's world. This was
  shown on Linux only.
- **Which WASI imports Rust's standard library brings.** The built component
  imports 14 WASI interfaces, all at `0.2.9`: `wasi:io/{poll,error,streams}`,
  `wasi:clocks/monotonic-clock` and `wasi:cli/{stdout,stderr,stdin,environment,
  exit,terminal-input,terminal-output,terminal-stdin,terminal-stdout,
  terminal-stderr}`. Unlike the note's earlier observation, nothing was at
  `0.2.0`. None is a filesystem, socket or HTTP interface, so the test host
  refuses any component that imports those.
- **Guest exports must be compiled only for WebAssembly.** `wit-bindgen`'s
  `export!` emits symbols named like `syrinx:plugin/commands@0.1.0#run`, which a
  native linker rejects. The template wraps `export!` in
  `#[cfg(target_arch = "wasm32")]` so the plugin's unit tests can link on the
  build machine. The generated types and import stubs do compile natively.
- **Generated guest code is `unsafe`.** wit-bindgen's glue uses `unsafe` and
  `export_name`; the template's workspace denies `unsafe_code` and allows it on
  the generated `bindings` module only. wasmtime's host bindings needed no such
  allowance.

## Gaps noticed but not changed

These need a decision in #28; the template does not invent one.

- **No export for a view's `cancel`.** The note's bridge has a `cancel`
  envelope that "reaches the plugin as a cancellation it may or may not honour",
  but the world has no export to deliver it: `host.cancel` goes the other way.
  The template's host accepts a `cancel` envelope and, since its calls are
  synchronous, has nothing pending to cancel. A real host with queued requests
  needs either a `views.cancel(view, request-id)` export or a rule that queued
  requests are dropped before delivery.
- **`commands.run` for a command declared with `form = true`.** The note does not
  say when the host calls `run` for a command that has a form. The template's
  `run` opens the Greetings tab, so both paths do something sensible, but #29
  should state the rule.
- **`views.opened` is delivered after the opening call returns.** The note's
  re-entrancy rule ("the host never calls a plugin export from inside one of that
  plugin's imports") means `host.open-view` cannot call `views.opened` itself.
  The test host queues it and calls `opened` once the export that opened the view
  has returned. #28 should write this ordering into the contract.
